> 前序事实源：`archive/137-stage88-external-agent-evidence-and-human-review.md`、`archive/136-stage87-single-work-item-controlled-execution.md`

## 1. 产品目标

在既有固定协作计划、单工作项受控派发、不可变执行证据和人工最终审阅之上，提供一条最多三轮的有限自动串行链路：

```text
操作者确认一次有界链路启动
  -> Harness 自动：规划者 -> 执行者 -> 审阅者
  -> Harness 归档候选、执行证据与审阅建议
  -> 操作者提交最终“通过 / 要求修改”
  -> 链路结束
```

操作者负责重大授权和最终业务决定，而不是为每一次正常角色交接重复点击确认。该能力仍不是自治循环、自动修改闭环或通用多 Agent 调度器。

## 2. 两类人工权限

### 2.1 启动授权（唯一执行授权）

`external-agent-chain start` 的 preview / `--commit` 是整条链路唯一的派发授权。确认摘要只绑定稳定事实：链路编号、任务、协作计划摘要、目标摘要、固定 Pi/OMP 拓扑、三个固定角色、审阅门与“最多三轮自动串行”限制。

确认摘要**不绑定** 15 秒实时状态快照。否则聊天、GUI 或人工核对的正常时延会让授权不可用；这不是降低安全性，而是将两种事实分离：

- 操作者批准稳定的业务范围和最大执行预算；
- Harness 在每次实际派发前重新读取并强制执行短时实时安全条件；`start --commit` 会在本机生成新的 UTC 运行时评估时间，而不是复用 preview 命令的旧时间，因此人工核对延迟不会把已确认的启动授权变成过期状态检查。

### 2.2 最终业务决定

规划、执行、审阅成功后，只有操作者可以提交 `approve` 或 `request_changes`。审阅建议不会自动采纳；`request_changes` 永远停止当前链路，不能自动生成新指令、修改、重试或再派发。

## 3. 自动串行的固定边界

只允许下列两种严格串行拓扑：

- `pi-local -> omp-local -> pi-local`；
- `omp-local -> pi-local -> omp-local`。

每条链路固定为一个目标、一个协作计划、一个规划轮次、一个执行轮次和一个审阅轮次。Harness 只能依次调用既有阶段 87 单工作项派发；不会启动宿主、开放工具、接受任意 argv/cwd/env、并行派发、网络、数据库、常驻服务、自动重试、自动重新规划、自动修改或自动批准。

规划候选和审阅建议仍是严格、已扫描、有界 JSON，不能改变 profile、工作项、路径、超时、结果上限、输入产物、审阅门或下游流程。

## 4. 每一轮的运行时 fail-closed 检查

启动授权通过后，不代表运行时可派发。规划者、执行者和审阅者的每一轮都必须在派发前重新检查：

1. 固定协作计划、任务、角色映射、拓扑和前序不可变摘要仍一致；
2. Harness 先等待固定两秒状态稳定窗口，然后仅执行一次当前目标的实时状态读取；目标必须是用户已打开的 Pi 或 OMP，且状态为新鲜 `observed` 与 `open`。该窗口不是派发重试，也不会重放已启动角色；
3. 宿主无活动工具、会话空闲，且既有单工作项 lease、started audit、唯一 terminal audit 和证据流程完整；
4. 上一轮输出通过大小、UTF-8、schema（适用时）、摘要和敏感信息扫描；审阅提示只绑定执行产物摘要和既有证据，不拼接原始执行文本，避免不受信内容改变审阅指令。

任一检查、宿主事件、结果归档或 JSON 解析失败，Harness 写入不可变 `stop` 记录并停止。它不会尝试下一角色、不会重试，也不会把失败解释为批准。

## 5. 不可变链路事实与恢复

`.runtime/external-agent-chain/v1/` 只保存安全、受限的不可变事实：

- `intent`：启动授权实际创建的链路意图；
- `planner-candidate`：规划候选及其来源执行证据摘要；
- `execution-receipt`：执行尝试、manifest 与产物摘要；
- `review-advice`：审阅建议及其来源候选和执行证据摘要；
- `stop`：角色和固定失败码；
- `finalization-pending` / `completion-receipt`：既有阶段 88 人工审阅与建议的精确绑定。

完成回执恢复仍先 preview、后用确认摘要与 `--commit`；只读取既有审阅和证据，绝不重新调用 Agent 或重复人工决定。

## 6. CLI 与只读投影

对外 CLI 只提供：

- `start`：预览或以一次确认启动自动三轮；
- `inspect`：只读显示链路、角色、证据、停止原因和门禁；
- `final-decision`：最终人工通过 / 要求修改；
- `recover-final-decision`：固定恢复完成回执。

不提供将正常自动链路拆回“规划 / 执行 / 审阅”三个人工提交步骤的 CLI。中文控制面板必须展示“自动串行中”“等待最终人工决定”“等待恢复最终决定”或“已停止（需新建链路）”，且不泄漏未扫描原文。

## 7. 验收标准

### 自动化

- 单次 `start --commit` 在 fixture 中按 `planner -> executor -> reviewer` 恰好一次串行执行，不出现 G2/G3 人工门禁；
- 启动确认摘要不因短时实时快照轮换而漂移，但每个角色仍在派发前读取新鲜 `open` 状态；
- 任一角色失败、超时、状态漂移、无效/超长/敏感输出或归档失败都会写入一次不可变停止记录，且绝不派发后续角色；
- 最终决定、pending 恢复、重复写入、候选/证据摘要漂移和中文只读投影均保持 fail-closed。

### 真实 Pi/OMP 验收

1. 由操作者分别打开无工具、空闲 Pi 与 OMP；
2. 对正向和反向拓扑各执行一次 `start` 的预览/提交；每次只确认启动与最终业务决定；
3. 检查三次真实尝试的连续宿主事件、唯一终态 audit、不可变产物、候选、建议和新进程读取；
4. 再执行一条失败路径，确认已写 `stop`、没有下一角色、没有重试和没有未释放 lease。

真实验收未成功前，不得以 fixture、旧阶段证据或过期状态快照声称完成。
